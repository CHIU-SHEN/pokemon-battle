# 卡牌标签人工复核操作指南

## 1. 复核范围

不需要一开始人工检查全部 1,267 张卡。按以下顺序处理：

1. 当前 `submission/deck.csv` 的 60 张牌。
2. `data/high_score_decks/*/deck.csv` 中 Top10 候选实际使用的牌。
3. 训练和评估中高频出现、自动标签可疑的牌。
4. 最后再按需要扩展到全卡库。

人工修改只写入 `data/manual_overrides.json`。不要直接编辑 `data/card_tags.json`，因为它是自动生成产物，下次运行生成脚本会覆盖手工修改。

## 2. 每张卡检查什么

先在 `data/cards.json` 中按 `card_id` 找到卡牌，核对：

- 英文名、日文名、阶段、HP、卡牌类型；
- 进化前身、规则框、ACE SPEC、ex/Mega ex 属性；
- 技能和攻击的效果文本；
- 搜索、抽牌、能量加速、换位、回收等效果是否被自动标签正确识别；
- 自动标签是否因文本关键词产生误判。

然后在 `data/card_tags.json` 中查看当前 `tags`。当前可使用的标签为：

```text
ace_spec, attach_energy, attacker, basic_energy, basic_pokemon,
damage_boost, deck_thinning, discard, draw, energy_discard,
evolution_pokemon, ex, gust, hand_refresh, heal, item,
main_attacker, mega_ex, prize_acceleration, recursion, risk_deckout,
search_energy, search_pokemon, setup_piece, stadium_control,
supporter, switch, tool, water_energy
```

其中模型当前直接使用的核心标签包括：

```text
basic_energy, water_energy, basic_pokemon, evolution_pokemon, ex,
main_attacker, search_pokemon, search_energy, attach_energy, draw,
supporter, item, tool, damage_boost, heal, discard, recursion,
deck_thinning, ace_spec
```

不要仅凭卡名判断，应以卡牌效果和在牌组中的实际职责为准。同一张卡可以有多个标签。

## 3. 记录人工修正

打开 `data/manual_overrides.json`，以字符串形式的卡牌 ID 增加记录：

```json
{
  "1145": {
    "add": ["search_pokemon", "deck_thinning"],
    "remove": ["draw"]
  }
}
```

- `add`：自动标签漏掉的正确标签。
- `remove`：自动规则误加的标签。
- 两个字段都保留为数组，没有内容时写 `[]`。
- 不要删除文件中其他卡牌的人工修正。
- 不要添加含义不明确、拼写不同或仅对一张卡临时有效的新标签。

判断示例：

- “从牌库找宝可梦加入手牌”：加入 `search_pokemon`，通常也可加入 `deck_thinning`。
- “抽 3 张牌”：加入 `draw`。
- “将弃牌区卡牌拿回手牌/洗回牌库”：加入 `recursion`。
- “交换自己的战斗宝可梦”：加入 `switch`。
- “把对手备战宝可梦换到战斗场”：加入 `gust`，不是 `switch`。
- 只出现“牌库”字样但没有抽牌效果：若自动产生 `draw`，应在 `remove` 中删除。

## 4. 重新生成并检查标签库

在项目根目录运行：

```powershell
& 'C:\Users\lenovo\miniconda3\envs\pokemon-tcg\python.exe' '.\src\cards\tags.py'
& 'C:\Users\lenovo\miniconda3\envs\pokemon-tcg\python.exe' '.\tests\test_card_db.py'
```

第一条命令根据自动规则和人工覆盖重新生成 `data/card_tags.json`；第二条命令检查卡牌数量、目标卡组关键卡牌和标签完整性。

随后再次打开对应卡牌，确认：

- `source` 已变为 `auto+manual`；
- `add` 中的标签已经出现；
- `remove` 中的标签已经消失；
- 测试输出 `OK: CardDB 1267 cards and key tags passed`。

## 5. 复核记录要求

每次提交一批人工修正时，在提交说明或独立复核表中记录：

| 字段 | 内容 |
| --- | --- |
| `card_id` | 引擎卡牌 ID |
| 卡名 | 用于人工阅读 |
| 原标签 | 修改前标签 |
| `add/remove` | 实际修正 |
| 依据 | 对应技能或攻击效果的简要说明 |
| 复核人和日期 | 责任追踪 |
| 规则版本 | 当前 Kaggle 比赛/引擎版本 |

效果依据应使用自己的简短概括，不要大段复制受版权保护的卡牌文字。

## 6. 训练数据重建

`option_features` 已经写入转换后的 JSONL。只重新生成 `card_tags.json` 不会自动更新已有训练样本。因此，完成一批标签复核并通过测试后，需要依次重新生成：

```powershell
& 'C:\Users\lenovo\miniconda3\envs\pokemon-tcg\python.exe' '.\scripts\convert_bad_cases.py' --with-v0
& 'C:\Users\lenovo\miniconda3\envs\pokemon-tcg\python.exe' '.\scripts\convert_kaggle_replays.py'
& 'C:\Users\lenovo\miniconda3\envs\pokemon-tcg\python.exe' '.\scripts\build_training_dataset.py'
& 'C:\Users\lenovo\miniconda3\envs\pokemon-tcg\python.exe' '.\scripts\audit_existing_data.py'
```

为了避免反复重建约 10 GB 的派生数据，应先集中完成当前目标卡组和 Top10 的一批复核，再统一执行上述命令。

最终验收条件：转换错误为 0、训练 manifest 的 `ok` 为 `true`、`unused_v1_labels` 为 0、`cross_split_games` 为空。

## 7. 什么时候可以把卡牌库标为 100%

至少满足：

- 当前目标卡组与 Top10 候选涉及的关键卡牌已人工复核；
- 人工修正全部记录在 `manual_overrides.json`；
- 卡牌来源、获取日期、文件哈希和 `ruleset_version` 已记录；
- 卡牌与标签测试通过；
- 标签变更后的失败对局、Kaggle 数据和正式训练集已重新生成并通过审计。
