# Kaggle 高分回放卡组筛选与最终卡组决策框架

## 1. 目标与基本原则

> 当前进度（2026-07-14）：10 副牌表已从完整 replay 的引擎 ID 无歧义落盘，10/10 通过静态合法性；阶段 B 已完成 2,500 局，10/10 为 0 异常、0 非法动作。按统一 `first-min` 参考成绩取前 8 进入阶段 C，但阶段 B 排名不得直接用于替换 `submission/deck.csv`。

目标是把 `实际比赛Top10与Kaggle高分回放卡组汇总.md` 中的 10 副 Kaggle 高分回放去重卡组全部转为可运行候选，经过同一套比赛矩阵筛选，最终保留 Top2：第 1 名作为主卡组候选，第 2 名作为备选卡组。两套都冻结独立牌表、Adapter、提交包和回归报告；只有主卡组通过发布门槛后才写入 `submission/deck.csv`。

机器可读规则固定在 `data/high_score_decks/top2_selection_policy.json`，后续循环赛汇总和冻结脚本必须读取或等价实现该口径。

需要特别注意：当前策略代码明显围绕 Abomasnow/水能体系设计。直接换牌表但继续使用原策略，会测到“新卡组与旧策略是否兼容”，而不是卡组本身强弱。因此比较分成两条线：

- **统一策略线**：使用尽量通用的合法动作策略，公平粗筛牌表。
- **卡组适配线**：每个晋级体系配套自己的规则权重/卡组 profile，比较可交付的“牌表 + 策略”整体强度。

最终选择依据是适配线；统一策略线只负责低成本淘汰明显不稳定的候选。

## 2. 初始候选池

6. Crustle / Mega Kangaskhan ex - Petrel

9. Marnie's Grimmsnarl ex - Tatsugiri / Petrel

同一体系的不同构筑必须作为独立候选，不能因为名字相近提前合并。

## 3. 数据落盘格式

每副候选牌表转换为：

```text
data/high_score_decks/<candidate_id>/deck.csv
data/high_score_decks/<candidate_id>/metadata.json
data/high_score_decks/<candidate_id>/mapping_report.json
```

其中：

- `deck.csv`：60 行引擎 card ID，可直接替换临时 submission 的牌表。
- `metadata.json`：体系、replay ID、原始名称、来源文档、卡组哈希。
- `mapping_report.json`：每行原始牌名、系列、编号、映射 card ID、是否唯一、错误信息。

split Alakazam 必须按 replay 中的两个 card ID 分开保留，不能只按英文名合并。

进入比赛前必须通过：60 张、非基本能量同 ID 不超过 4、ACE SPEC 不超过 1、至少一张基础宝可梦、所有 ID 均存在于 `cards.json`。

## 4. 四阶段筛选

### 阶段 A：静态校验

淘汰条件：映射不唯一且无法人工确认、卡牌不存在、牌数不为 60、引擎判定非法。

静态 proxy 只用于排序运行顺序，不得用来直接选 Top2。

### 阶段 B：冒烟与稳定性（10 副 → 最多 8 副）

每副卡组使用统一策略运行：

- 自镜像 50 局
- 对 Random 100 局
- 对 FirstMin 100 局

硬淘汰条件：非法动作率大于 0、异常退出、不能完成对局、超时明显超过提交预算。胜率只作参考。

### 阶段 C：统一策略粗筛（最多 8 副 → 4 副）

每副候选使用相同策略版本、相同 seed 集合、先后手互换，对以下对手各 500 局：

- Random
- Sample
- Exploiter-FirstMin
- V0-best

计分采用保守指标，避免只刷 Random：

```text
screen_score = 0.15*WR_random + 0.20*WR_sample
             + 0.30*WR_exploiter + 0.35*WR_v0_best
             - stability_penalty
```

同时保留各体系至少一副最优构筑进入复核；若某体系所有候选都明显低于门槛则不强行保留。

### 阶段 D：策略适配复赛（4 副 → 2 副）

为四副候选分别建立最小可用 profile：主攻手、进化链、贴能目标、检索优先级、撤退/换位、关键 Trainer、终局目标。不得继续套用 Abomasnow 专属常量。

每个“牌表 + 适配策略”对固定对手各 1,000 局，并进行候选间循环赛。所有对局使用成对 seed 和先后手交换。

复赛评分：

```text
finalist_score = 0.55*external_baseline_score
               + 0.25*round_robin_score
               + 0.10*worst_matchup_score
               + 0.10*stability_score
```

选择前二，不因单项 Random 胜率高直接晋级。

### 阶段 E：决赛与冻结（2 副 → Top2 主备）

两副决赛卡组对每个固定外部对手至少 3,000 局，并进行至少 3,000 局直接对战。要求：

- 使用完全相同的 seed 清单并交换先后手。
- 报告胜率、95% 置信区间、最差对局、非法动作率、P95 决策耗时。
- 主卡组对关键外部基线的提升应有置信证据；区间重叠严重时追加对局。
- 进行消融：只换 deck、只换 strategy、deck+strategy，确认收益来源。
- 两套都必须通过 `tests/` 全量回归和独立提交包自检；第 1 名标记为 primary，第 2 名标记为 reserve。

## 5. 最终选择规则

候选必须先通过以下硬门槛：

- 合法动作率 100%，无异常退出。
- 满足 Kaggle 时间和包体限制。
- 对 Exploiter-FirstMin、V0-best 无不可接受退化。
- 不依赖 replay 中的隐藏信息。
- 牌表与策略 profile 均能在最终提交包内稳定加载。

在通过硬门槛的候选中，按以下优先级决定 Top2 排名：

1. 外部基线加权胜率。
2. 最差对局胜率，而非最好对局。
3. 候选间循环赛成绩。
4. 95% 置信区间下界。
5. 稳定性和决策延迟。

若前两名综合差距小于 1 个百分点且置信区间无法区分，仍同时保留，并以异常更少、最差对局更高、策略更简单者作为主卡组，另一套作为备选卡组。若第 2 名与第 3 名也无法区分，应追加对局后再冻结 Top2。

## 6. 实验目录与结果表

每次实验输出到：

```text
experiments/high_score_deck_selection/<stage>/<candidate_id>/<opponent>/
```

总榜固定字段：

| 字段 | 含义 |
| --- | --- |
| candidate_id | 不随名称变化的候选 ID |
| deck_sha256 | 牌表版本哈希 |
| strategy_version | 策略代码/profile 版本 |
| opponent | 固定对手 |
| games / seed_set | 局数与种子集合 |
| first/second split | 先后手分层结果 |
| W/L/D、win_rate、CI95 | 核心结果 |
| illegal / exceptions | 稳定性硬指标 |
| latency_p50/p95 | 性能指标 |
| stage_score | 当前阶段加权分 |
| decision | 晋级、淘汰或追加对局 |

任何对 deck、策略或规则的改动都会生成新版本，不能与旧结果直接混算。

## 7. 实现顺序

1. 写牌名/系列/编号到引擎 card ID 的唯一映射器，导入 10 副牌表。
2. 为每副牌生成合法性报告和哈希。
3. 建立临时候选 submission，不能在筛选阶段覆盖正式 `submission/deck.csv`。
4. 扩展 `eval/league.py`，支持候选清单、共同 seed 和先后手成对比较。
5. 先跑阶段 B，确认所有体系可被引擎和策略正常使用。
6. 跑统一策略粗筛，再为前四名编写卡组 profile。
7. 完成复赛、决赛、消融和回归测试。
8. 最终报告确认 Top2 后，分别构建 primary/reserve 提交包并冻结哈希；只把通过发布门槛的主卡组复制到正式 submission。

当前最近的实现任务不是马上跑胜率，而是先完成 **10 副牌表的无歧义 card ID 映射**；映射错误会让后续所有排名失效。
