## 2. 已直接处理的内容

运行：

```powershell
python scripts/audit_existing_data.py
```

脚本会生成以下可追溯产物：

| 产物 | 用途 |
| --- | --- |
| `data/processed/local_data_audit.json` | 全仓库数据数量、覆盖率、可用性审计 |
| `data/processed/target_deck_profile.json` | 目标卡组卡名、数量、类型、HP、标签、卡组哈希 |
| `data/processed/bad_case_index.json` | 600 个失败案例的路径、对局、步数、原因索引 |
| `data/training/training_manifest_v1.json` | 正式训练集哈希、切分、监督来源、权重与泄漏审计 |

当前 Windows 开发环境使用 Conda 环境 `pokemon-tcg`（Python 3.11）；上述审计产物已实际生成并通过 JSON 解析检查。

## 3. 现有数据可以直接做什么

### A. 目标卡组与卡牌数据（现在即可做）

- [x] 检查目标卡组是否为 60 张。
- [x] 将卡牌 ID 关联到名称、类型、HP 和功能标签。
- [x] 为目标卡组生成稳定哈希，追踪版本变化。
- [ ] 人工复核主攻手、辅助、检索、抽牌、回收、换位、能量加速等关键标签。
- [ ] 给卡牌库补充 `source_url`、`retrieved_at`、`ruleset_version`；这些信息无法从现有文件可靠推断。

验收：目标卡组每个 ID 在 `cards.json` 和 `card_tags.json` 中都有唯一记录；总数为 60；同名版本不错误合并。

### B. 600 个失败日志（已转换并完成第一批老师补标）

现有日志每局包含 `trace`，每步已有行动玩家、可见 observation、选项、实际动作和最终结果。因此可直接派生：

- `game_id / decision_id / player / turn`
- 可见局面特征、合法选项、实际动作
- 最终胜负、动作耗时、对局双方策略名称
- 公开日志序列和基础困难样本标签

仍不能从原始日志直接可靠派生：

- 未运行搜索时的 V1 候选访问量、Q 值和风险分位数
- 真实高手动作标签
- 双方真实牌表 ID（日志若未明确保存，不应猜测）
- 精细失败原因（如“错过击倒”）——需要规则检测器或搜索反事实验证

处理要求：

- [x] 使用来源目录与 `case_id` 组成全局唯一 `game_id`，保留原文件路径；已处理两个不同对局共用同一 `case_id` 的碰撞。
- [x] 每步只使用行动者可见的 observation，禁止解码或加入隐藏全状态。
- [x] 唯一动作样本已用 `quality.forced_single_option` 单独标记，训练时应降采样。
- [x] 先输出 `observed_action` 与 `game_result`；没有搜索时，老师字段置空，不能拿实际动作冒充老师动作。
- [x] 已对目标卡组行动方的 9,832 条基础样本补当前 V0 规则动作并逐条做合法性校验；对手方不错误套用目标卡组规则。

## 5. 正式训练样本的最低 schema

每条逐步样本必须包含：

| 字段组 | 必填内容 | 缺失时怎么处理 |
| --- | --- | --- |
| 身份 | schema、game_id、decision_id、player、turn、ruleset | 不进正式集 |
| 输入 | 行动者可见状态、截至当前的公开事件 | 不可补未来信息 |
| 动作 | 全部合法动作、稳定动作 ID、实际动作 | 无合法动作集合时不训练 policy |
| 老师 | V0 动作；V1 候选分数/访问量/排名 | 没跑老师就置空 |
| 结果 | 最终胜负、value、risk | 只训练实际存在的目标 |
| 卡组 | 双方 deck_id、特征、相似度 | 未知就置空，不猜测 |
| 来源 | source、quality、weight、生成器版本 | 无来源不进入正式集 |

同一 `game_id` 必须整体进入 train、valid 或 test 中的一个集合，禁止按决策随机切分。
