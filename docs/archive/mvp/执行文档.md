## 0. 一句话执行策略

不要一开始就做大模型或纯 PPO。先做一个**永不崩溃、能稳定提交、卡组特化的强规则 Agent**，再逐步加上**隐藏信息采样、有限搜索、搜索蒸馏和卡组协同进化**。

推荐执行路径：

```text
第 1 层：可提交工程骨架
    ↓
第 2 层：V0 卡组特化强规则 Agent
    ↓
第 3 层：评估系统 + 对局日志 + 回归测试
    ↓
第 4 层：V1 约束粒子信念 + 有界搜索 BG-GEM
    ↓
第 5 层：卡组知识库 + 卡组优化
    ↓
第 6 层：V2 小模型蒸馏 + 联赛/稳健性
    ↓
最终冻结：提交包、消融、说明文档
```

核心原则：

- 每一周都必须有一个可提交版本；
- 每次加复杂模块，都要和上一版做胜率对比；
- 搜索、模型、卡组优化都不能牺牲稳定性；
- 排行榜只是参考，真正决策看本地统计显著结果。

## 2. 里程碑总览

| 阶段 | 目标 | 主要产出 | 通过标准 |
|---|---|---|---|
| M0 | 冻结环境与基准 | 可运行本地评估、随机/样例基线 | 1000 局无崩溃，有胜率/耗时报告 |
| M1 | V0 强规则 Agent | 卡组特化规则策略、兜底策略 | 稳定击败随机和弱规则基线 |
| M2 | 评估系统 | 对局矩阵、统计晋级、日志分析 | 每次改动可判断强弱 |
| M3 | V1 搜索 Agent | belief、动作候选、BG-GEM 搜索 | 相比 V0 有显著胜率提升 |
| M4 | 卡牌知识与卡组优化 | 卡牌标签、合法性检查、MAP-Elites | 产生多套强候选卡组 |
| M5 | V2 蒸馏模型 | 小模型 policy/value、搜索蒸馏 | 同等时间预算下强于 V1 或更快 |
| M6 | 联赛与冻结 | 主提交包、备份包、消融说明 | 连续回归稳定，无超时/非法动作 |

推荐优先级：

1. M0–M2 必做；
2. M3 是冲高分主力；
3. M4 取决于是否发现明显强卡组空间；
4. M5 只有当 V1 已稳定并积累足够高质量数据后再做；
5. M6 必做，不要最后一天才整理提交。

## 4. M1：V0 卡组特化强规则 Agent

### 4.1 任务目标

做一个低延迟、稳定、可解释的强基线。V0 是之后搜索和模型的安全底座。

V0 要解决三个问题：

1. 不非法、不超时、不崩溃；
2. 对主卡组的核心打法足够懂；
3. 在搜索失败或模型不可用时能兜底。

### 4.2 V0 总体方法

V0 使用“规则打分 + 上下文特化 + 安全兜底”：

```text
observation
  → 解析 select/context/options
  → 根据 context 选择规则模块
  → 给每个合法 option 或联合动作打分
  → 满足 min/maxCount 后返回最优列表
  → 如果规则不认识，进入 fallback
```

### 4.3 具体任务

#### 任务 M1-1：写 observation 解析层

方法：

- 把官方 observation 转成内部结构：
  - 当前玩家；
  - 自己/对手奖赏卡数；
  - Active Pokémon；
  - Bench；
  - 手牌；
  - 牌库数量；
  - 弃牌区；
  - 当前 select；
  - 当前 log 增量。
- 对字段缺失或新增字段保持兼容。

产出：

- `parser.py`；
- `ParsedState`；
- `ParsedSelect`；
- `GameLedger` 的初始接口。

验收：

- 能解析 1000 局随机对战日志；
- 未知字段不影响 agent 返回动作。

#### 任务 M1-2：写合法动作兜底

方法：

按照优先级返回安全动作：

1. 如果 `minCount == 0` 且可以不选，优先不选；
2. 如果是必须选，选择低风险 option；
3. 如果 option 有卡牌 ID，按基础价值排序；
4. 如果 option 不可识别，返回前 `minCount` 个；
5. 对 `maxCount` 不盲目选满，除非 context 明确需要。

产出：

- `fallback.py`；
- `safe_action(select)`。

验收：

- 任意合法 select 都能返回合法 action；
- 随机生成 10,000 个 select 样本不非法。

#### 任务 M1-3：主卡组核心战术规则

以样例 Mega Abomasnow ex 水系卡组为起点，先做卡组特化规则。

方法：

- 建立卡牌 ID 常量表；
- 标注关键卡：
  - 基础水能量；
  - Snover；
  - Mega Abomasnow ex；
  - Mega Signal；
  - Lillie's Determination；
  - Waitress；
  - Cyrano；
  - Maximum Belt；
- 为不同阶段设定优先级：
  - 开局：找基础 Pokémon、建立进化线；
  - 中盘：进化、贴能、检索、压血；
  - 终局：计算伤害线、奖赏卡交换、避免 deck-out。

具体规则方向：

- 开局手牌选择：
  - 优先能展开的基础 Pokémon；
  - 避免只有高风险单 Pokémon 时过度保守；
- Bench：
  - 保证至少一条后续进化线；
  - 不盲目铺满，给关键 Pokémon 留格子；
- 贴能：
  - 优先给即将攻击或下回合可攻击的 Active/Bench；
  - 如果 Active 即将被击倒，给后排主攻；
- 检索：
  - 缺基础找基础；
  - 缺进化找 Mega Abomasnow ex；
  - 缺能量找能量；
  - 终局优先找能直接结束比赛的牌；
- 攻击：
  - 能拿奖赏卡时优先；
  - 能击倒高价值 ex/Mega 时加权；
  - 对需要弃牌库顶的攻击，估计剩余基础水能量密度和 deck-out 风险。

产出：

- `rules.py`；
- `deck_profile_abomasnow.py`；
- 一份卡组策略说明。

验收：

- V0 vs 随机胜率显著高；
- V0 mirror 不出现明显弱智操作；
- 对核心 context 的动作选择可以解释。

#### 任务 M1-4：规则调参表

方法：

不要把所有分数硬编码在散乱 if 里。建立一张可调权重表：

```python
WEIGHTS = {
    "take_prize": 1000,
    "ko_ex_bonus": 500,
    "setup_main_attacker": 300,
    "attach_to_ready_attacker": 250,
    "avoid_deckout": 800,
    "waste_supporter_penalty": -200,
}
```

验收：

- 调权重不需要改策略代码结构；
- 实验报告中能记录权重版本。

### 4.4 V0 晋级标准

V0 进入下一阶段前，应满足：

- 10,000 局本地对战无崩溃；
- 非法动作次数为 0；
- p95 单决策耗时远低于比赛限制；
- 比随机/样例弱基线强；
- 有稳定日志和可复现实验编号。

## 5. M2：评估系统和实验纪律

### 5.1 任务目标

让每一次改动都有可信结论：到底变强了、变弱了，还是只是随机波动。

### 5.2 具体任务

#### 任务 M2-1：对局矩阵

方法：

维护固定基线池：

- Random；
- 官方 sample；
- V0 当前版；
- V0 历史最佳版；
- V1 搜索版；
- 不同卡组版本；
- 专门针对主策略的 exploiter。

每次评估输出矩阵：

| A \\ B | Random | Sample | V0-best | V1-best | Exploiter |
|---|---:|---:|---:|---:|---:|
| candidate | ... | ... | ... | ... | ... |

验收：

- 新版本必须和至少 3 个基线比较；
- 不只看 mirror。

#### 任务 M2-2：统计晋级规则

方法：

采用分层晋级：

1. 快筛：200–500 局，明显差的直接淘汰；
2. 中筛：1000–3000 局，观察稳定提升；
3. 终筛：5000–20000 局，对主候选做置信区间。

晋级标准建议：

- 胜率提升 > 2% 且置信区间不明显跨 0；
- 非法/崩溃/超时为 0；
- 平均耗时不超过当前预算；
- 对 exploiter 不明显变弱。

验收：

- `eval/stats.py` 能输出 Wilson 区间或 bootstrap 区间；
- 实验报告自动标注“晋级/观察/淘汰”。

#### 任务 M2-3：日志与错误样本库

方法：

保存以下样本：

- 输掉但本可翻盘的局；
- 搜索和规则选择不同的局；
- 高耗时局；
- 终局 deck-out；
- 非法动作前的 observation；
- 对手关键隐藏信息导致误判的局。

产出：

- `logs/bad_cases/`；
- `eval/replay_case.py`。

验收：

- 可以从某个 bad case 复现 agent 的选择；
- 可以比较不同版本在同一个局面的动作。

### 5.3 本阶段关键提醒

排行榜分数会有噪声，也会受对手分布影响。不要因为一次提交涨跌就大改方向；用本地矩阵决定大部分工程选择。

## 6. M3：V1 约束粒子信念 + BG-GEM 有界搜索

### 6.1 任务目标

在关键决策上，用官方 Search API 进行小预算高质量搜索，解决规则 Agent 的短视问题。

V1 不追求全局大树 MCTS，而是只在根部或少量深度上做固定预算搜索。

### 6.2 V1 模块结构

```text
ParsedState
  → GameLedger：记录已知信息
  → BeliefSampler：采样隐藏状态粒子
  → ActionGenerator：生成 K 个完整联合动作候选
  → BGGemSearcher：对候选做粒子化评估和顺序淘汰
  → RiskSelector：按均值/方差/CVaR/先验选择
```

### 6.3 具体任务

#### 任务 M3-1：精确账本 GameLedger

方法：

用 observation 和 log 维护：

- 已知手牌；
- 己方牌库剩余集合；
- 己方奖赏卡可能集合；
- 对手已展示牌；
- 对手弃牌区；
- 对手场上 Pokémon；
- 对手可推断手牌；
- 已使用 Supporter/能量等回合状态。

注意：

- 不要把看不到的对手手牌当未知均匀随机即可；
- 检索、抽牌、洗牌、弃牌都会改变后验；
- prize 和 deck 顺序非常影响主卡组价值。

验收：

- 每一步 ledger 的卡牌数量守恒；
- 已知公开信息和 observation 一致；
- 遇到不认识的 log 不崩溃，而是降级到保守 belief。

#### 任务 M3-2：约束粒子采样

方法：

从账本中采样完整隐藏状态：

- 己方未知牌库顺序；
- 己方奖赏卡；
- 对手手牌；
- 对手牌库；
- 对手奖赏卡；
- 对手盖住的 Active 信息。

约束：

- 不能出现已公开在别处的牌；
- 数量必须和 observation 一致；
- 已由日志推断的卡要固定；
- 对手卡组未知时，从候选 archetype 或公开卡牌分布中采样。

采样策略：

- 早期：简单约束随机采样；
- 中期：按对手已展示牌推断 archetype；
- 后期：按检索/抽牌历史调整手牌后验。

验收：

- 采样 10,000 个粒子都合法；
- 用粒子喂给 `search_begin` 不崩溃；
- 对同一局面采样多次，结果有合理多样性。

#### 任务 M3-3：联合动作候选生成

方法：

不要把每个 option 当成独立分类。生成完整 action list。

候选来源：

1. V0 规则最优动作；
2. V0 规则 top-k 变体；
3. 启发式特殊动作：
   - 少选而不是选满；
   - 保留资源；
   - 冒险抢奖；
   - 防守换人；
4. 小模型 policy top-k；
5. 少量随机合法扰动。

对可变长度选择：

- 如果是“最多选 k 张”，显式生成长度 0..k 的候选；
- 如果选择顺序有意义，保留有序列表；
- 如果无序，规范化排序去重。

验收：

- 每个候选都是合法 action；
- 候选数量 K 通常控制在 4–16；
- 包含 V0 动作作为安全候选；
- 能记录每个候选来源和先验分。

#### 任务 M3-4：Search API 生命周期封装

方法：

实现安全封装：

```text
search_begin(...)
try:
    search_step(...)
    search_step(...)
finally:
    search_end(...)
```

要求：

- 每次根搜索必须有节点预算；
- 每个分支不再使用要释放；
- 异常时回到 V0；
- 搜索内存高水位要记录；
- manual_coin=True 时硬币作为 chance node，而不是当作玩家策略。

验收：

- 反复搜索 10,000 次内存不无限增长；
- 超预算时能停止并返回当前最好动作；
- Search API 抛错时不影响提交。

#### 任务 M3-5：实现 BG-GEM 根搜索

方法：

对当前局面：

1. 生成 K 个候选动作；
2. 为每个候选加入 Gumbel 噪声，选出初始评估集合；
3. 抽取 P 个隐藏状态粒子；
4. 每轮给存活候选分配等量评估；
5. 通过 Search API 走若干步；
6. 叶节点用启发式价值或小模型价值；
7. 淘汰表现差的候选；
8. 最终根据风险敏感分数选择。

推荐初始预算：

| 档位 | 使用场景 | K | P | 节点上限 |
|---|---|---:|---:|---:|
| Fast | 普通小决策 | 4 | 4 | 128 |
| Normal | 主阶段/攻击选择 | 8 | 8 | 512 |
| Tactical | 可能拿奖/被击倒 | 12 | 12 | 1024 |
| Critical | 终局关键选择 | 16 | 16 | 2048 |

价值函数初期可用启发式：

```text
V = 奖赏卡优势
  + 场面攻击准备度
  + 可击倒威胁
  + 手牌/资源质量
  + 牌库剩余安全性
  - 被反杀风险
  - deck-out 风险
```

验收：

- V1 vs V0 在主评估矩阵中有显著提升；
- 平均耗时在预算内；
- 搜索选择不同于 V0 的局面能解释；
- 如果搜索关闭，Agent 自动退化为 V0。

#### 任务 M3-6：对手节点处理

方法：

不要简单假设对手随机。采用混合模型：

```text
V_opp = (1 - rho) * V_policy + rho * V_best_response
```

- `V_policy`：对手规则/模型策略的期望；
- `V_best_response`：对手有限预算最坏响应；
- `rho`：对手强度/关键程度，建议 0.2–0.6 动态调整。

动态规则：

- 对手明显能拿奖时，提高 `rho`；
- 对手资源少或动作不关键时，降低 `rho`；
- 终局提高 `rho`。

验收：

- 比“对手随机”搜索更稳；
- 比“对手永远最优”不过分保守。

### 6.4 V1 晋级标准

- 在固定卡组下，V1 相比 V0 胜率显著提升；
- 至少 5000 局无非法/崩溃；
- p95 决策耗时可控；
- 内存高水位可控；
- 关键 bad case 明显减少。

## 8. M5：卡组优化与策略协同进化

### 8.1 任务目标

找到比样例 deck 更适合当前 Agent 和对手分布的卡组，同时避免只对弱基线过拟合。

### 8.2 基本思路

卡组优化不是随机改 60 张牌，而是“结构化搜索”：

```text
合法卡组生成
  → 快速代理评估
  → 多样性保留 MAP-Elites
  → 高潜力卡组多局评估
  → 与策略版本共同进化
```

### 8.3 具体任务

#### 任务 M5-1：卡组合法性检查器

方法：

实现真实规则：

- 总数 60；
- 非基础能量同名最多 4；
- ACE SPEC 最多 1；
- 至少 1 张 Basic Pokémon；
- Card ID 合法；
- 其他官方限制。

验收：

- 样例 deck 合法；
- 随机非法 deck 能被准确拒绝；
- 输出错误原因。

#### 任务 M5-2：卡组原型定义

方法：

不要在全卡池中完全随机。先定义 archetype：

- Mega Abomasnow 水能量高密度；
- 更稳定展开型；
- 更激进抢奖型；
- 更厚防守/回复型；
- 针对主流 ex/Mega 的 tech 型。

每个 archetype 定义：

- 核心 Pokémon 线；
- 能量数量范围；
- draw/search/supporter 范围；
- tech 卡槽；
- ACE SPEC 选择。

验收：

- 每个 archetype 能生成至少 100 个合法变体；
- 每个变体有标签和参数。

#### 任务 M5-3：协同图和 deck score

方法：

用 CardDB 和对局数据构建卡牌协同：

- 卡 A 搜索卡 B；
- 卡 A 为卡 B 提供能量；
- 卡 A 提高卡 B 伤害；
- 卡 A 降低卡 B 风险；
- 卡 A 和卡 B 抢同一回合资源则负协同。

deck 初筛分：

```text
DeckScore =
  展开稳定性
  + 主攻成型速度
  + 能量一致性
  + 抽牌/检索密度
  + 终局能力
  + 对主流威胁覆盖
  - 卡手风险
  - deck-out 风险
```

验收：

- 初筛前 10% 卡组在实战中明显优于随机卡组；
- 协同分能解释卡组为什么被选中。

#### 任务 M5-4：MAP-Elites 多样性搜索

方法：

不要只保留胜率最高的单一方向。用特征格子保留多样卡组：

特征建议：

- 能量数量；
- 主攻类型；
- draw/search 比例；
- 平均成型回合；
- 防守/回复密度；
- tech 卡数量；
- deck-out 风险。

每个格子保留当前最优卡组。

验收：

- 不是只产出一堆同质 deck；
- 至少保留 20–50 个有差异的候选；
- 高分候选进入中筛实战。

#### 任务 M5-5：卡组-策略共同进化

方法：

每轮：

1. 用当前 Agent 评估候选 deck；
2. 选出强 deck；
3. 针对强 deck 微调规则/搜索权重；
4. 新 Agent 再评估 deck；
5. 引入 exploiter 检查是否过拟合。

验收：

- 新 deck + 新策略整体强于旧 deck + 旧策略；
- 单独替换 deck 或策略也要记录效果；
- 不选只在弱对手上强、对强对手脆的 deck。

## 9. M6：V2 小模型蒸馏

### 9.1 任务目标

把 V1 搜索的高质量决策蒸馏成一个轻量 policy/value 模型，用于：

- 更快生成候选动作；
- 更准评估叶节点；
- 降低搜索预算；
- 提升复杂局面的泛化。

### 9.2 何时开始 V2

必须同时满足：

- V1 已稳定；
- 有至少数十万条高质量搜索决策数据；
- 评估系统可靠；
- 当前瓶颈确实是候选生成或叶值质量，而不是工程 bug。

如果不满足，继续加强 V1，不要提前训练模型。

### 9.3 具体任务

#### 任务 M6-1：数据采集

方法：

从 V1 搜索保存训练样本：

- observation 特征；
- select/context/options；
- legal mask；
- V0 候选；
- 搜索访问次数；
- 搜索 Q 值；
- 最终选择；
- 对局结果；
- 搜索预算档位；
- 是否关键局面。

注意：

- 可以在训练中使用本地完整隐藏状态做 teacher；
- 最终推理模型只能使用比赛可见 observation；
- 不要泄露真实隐藏信息到提交时的输入特征。

验收：

- 数据 schema 固定；
- 能检查样本合法性；
- train/valid 按对局切分，避免同局泄露。

#### 任务 M6-2：特征表示

方法：

初期不要上大 Transformer。使用轻量结构：

- 卡牌 ID embedding；
- zone embedding；
- owner embedding；
- count/HP/damage/energy 数值特征；
- select option 局部特征；
- 回合状态特征；
- 已知/未知 mask。

模型规模建议：

- 1M–5M 参数；
- CPU 推理毫秒级；
- 能导出 TorchScript/ONNX 或纯 NumPy fallback。

验收：

- 单次前向耗时满足提交预算；
- 在验证集上 policy top-k 命中搜索动作；
- value 与实战结果/搜索 Q 有正相关。

#### 任务 M6-3：多任务训练

训练目标：

- policy：预测搜索改进后的动作分布；
- value：预测胜率或奖赏卡优势；
- risk：预测下行风险；
- optional belief：预测隐藏信息分布摘要。

损失：

```text
Loss = CE(policy_search)
     + λv * MSE(value)
     + λr * MSE(risk)
     + λreg * regularization
```

验收：

- 模型候选生成强于纯规则 top-k；
- 作为叶值时 V1 搜索胜率提升；
- 如果只提升离线指标、不提升实战，则不合入主线。

#### 任务 M6-4：Search Reanalysis

方法：

用最新模型重新搜索旧样本中的关键局面：

- 重点选高分歧局面；
- 重点选终局；
- 重点选 V0/V1 选择不同的局面；
- 重点选模型置信高但输掉的局面。

验收：

- Reanalysis 数据能提升下一版模型；
- 不让数据集被大量低价值普通决策淹没。

### 9.4 V2 晋级标准

V2 只有在以下条件满足时进入主提交：

- 同等时间预算下胜率高于 V1；
- 或胜率相近但耗时明显更低；
- 或在未知卡组/不同 deck 上泛化明显更好；
- 且没有引入依赖、序列化、推理崩溃风险。

否则 V2 作为实验分支，不影响 V1 主提交。

## 10. 搜索预算和时间管理

### 10.1 决策分级

把所有 select 分成四类：

| 类别 | 示例 | 策略 |
|---|---|---|
| trivial | 只有 1 个合法动作 | 直接返回 |
| routine | 普通抽牌/检索小选择 | V0 或 Fast 搜索 |
| tactical | 贴能、攻击、换人、进化 | Normal/Tactical 搜索 |
| critical | 能拿奖、会被击倒、终局 | Tactical/Critical 搜索 |

### 10.2 时间预算建议

比赛按整场对局限制，而不是每步固定时间。Agent 应维护本局已用时间。

策略：

- 前期展开：保守用时；
- 中期关键回合：正常搜索；
- 终局：可以多用；
- 如果本局剩余时间低，自动降级；
- 如果 option 很少且 V0 很确定，不搜索。

### 10.3 超时保护

每次 agent 调用：

1. 记录开始时间；
2. 先算 V0 动作；
3. 如果时间充足再搜索；
4. 搜索循环每轮检查时间；
5. 超时前返回当前最好动作；
6. 任何异常返回 V0。

验收：

- 人为设置很低时间预算时仍能返回合法动作；
- 搜索永远不是唯一可用路径。

## 11. 提交包工程要求

### 11.1 agent 入口

`main.py` 必须简洁稳定：

```text
agent(obs_dict)
  if obs indicates deck request:
      return deck
  try:
      return Agent.act(obs_dict)
  except Exception:
      return safe_fallback(obs_dict)
```

要求：

- 不在每次调用重复加载大型数据；
- 全局缓存只初始化一次；
- 不写绝对路径依赖；
- 不依赖本地训练文件；
- 不打印大量日志；
- 不在提交包中放无用大文件。

### 11.2 依赖策略

优先级：

1. Python 标准库 + 官方 SDK；
2. NumPy；
3. 轻量模型运行时；
4. 避免大型深度学习依赖，除非 Kaggle 环境明确支持且测试通过。

### 11.3 版本冻结

最终至少保留三份提交：

- `submission_safe_v0`：纯规则稳定版；
- `submission_search_v1`：主力搜索版；
- `submission_model_v2`：如果验证显著更强，作为最终候选。

不要只有一份复杂最终版。比赛后期最怕“理论最强但提交崩”。

## 14. 必须做的消融实验

每个模块都要证明“值得存在”。

| 消融 | 对比目的 |
|---|---|
| V0 vs Random/Sample | 证明规则底座有效 |
| V1 搜索 vs V0 | 证明搜索有效 |
| belief 粒子 vs 单一 determinization | 证明隐藏信息建模有效 |
| BG-GEM vs 简单 top-k rollout | 证明顺序淘汰有效 |
| 风险敏感选择 vs 均值最大 | 证明稳健性有效 |
| 对手混合响应 vs 对手随机 | 证明 opponent model 有效 |
| 小模型候选 vs 规则候选 | 证明模型有效 |
| 新 deck vs 旧 deck | 证明卡组优化有效 |
| 新 deck + 旧策略 / 旧 deck + 新策略 | 分离 deck 和策略贡献 |

如果某个模块消融不提升，就不要为了“技术先进”保留它。高分方案应该像一把好刀：锋利、轻、不多余。

## 15. 风险与止损标准

### 风险 1：搜索变慢或内存高

止损：

- 降低节点预算；
- 只在 critical/tactical 局面搜索；
- 粒子数从 16 降到 4–8；
- 关闭深层对手搜索；
- 回退 V0。

### 风险 2：belief 错误导致搜索误判

止损：

- 搜索结果必须和 V0 比较；
- 若搜索置信低或粒子方差高，返回 V0；
- 增大风险惩罚；
- 修 ledger 数量守恒和后验逻辑。

### 风险 3：模型离线好、实战差

止损：

- 模型只用于候选 prior，不直接决策；
- 加强 DAgger；
- 检查训练/验证泄露；
- 如果实战不提升，V2 不进主提交。

### 风险 4：卡组搜索过拟合弱对手

止损：

- 强制进入对局矩阵；
- 加 exploiter；
- 保留多个 archetype；
- 不只看对随机胜率。

### 风险 5：最后阶段大改导致提交崩

止损：

- 最后一周冻结；
- 保留 safe_v0；
- 每次提交前跑回归；
- 不引入新依赖。

### Strategy 叙事

建议表述：

> 我们没有依赖单一黑箱模型，而是构建了一个面向不完全信息卡牌游戏的分层系统：底层是卡组特化安全策略和精确规则账本，中层用约束粒子表示隐藏信息，并用固定预算的 Gumbel 顺序淘汰搜索做局部策略改进，上层再把搜索结果蒸馏到轻量模型，并通过多卡组联赛和协同进化提高泛化与稳健性。
