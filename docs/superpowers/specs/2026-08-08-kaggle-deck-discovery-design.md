# Kaggle 全榜卡组发现与动态聚类设计

## 目标

建立一条独立、可恢复的卡组发现管线，广度优先扫描 Pokémon TCG AI Battle 的公开排行榜、队伍、active submissions 和少量 episode，从 replay 中仅提取双方完整 60 卡牌组。第一阶段不批量保存完整对局训练数据；先建立尽可能全面的卡组目录并动态聚类，第二阶段才按类别定向采集完整对局。

本设计解决现有数据集中在少量已知 submission、404 套精确卡组和固定 Top10 候选附近的问题。现有训练、MCTS、原始 replay 与候选产物不在本次改动范围内。

## 已验证的外部规模

2026-08-08 通过 Kaggle 官方 CLI 下载的公开排行榜快照包含 6,519 支队伍；排行榜文件时间为 2026-08-07 16:41:50。现有本地归档包含 5,974 个 replay，其中 5,952 个通过完整轨迹检查，共得到 404 套精确去重卡组。完整榜单因此仍有明显的发现空间。

## 架构

管线按以下顺序运行：

1. 枚举完整排行榜并记录 team ID、排名、分数和快照时间。
2. 枚举每支队伍的公开 active submissions，第一轮选择最新有效 submission。
3. 为每个选中 submission 获取最近 3 个完整 episode。
4. 在全局范围按 episode ID 去重。
5. 将单个 replay 下载到专用临时目录。
6. 从 replay 中提取双方完整卡组、队伍、submission、episode、时间和胜负元数据。
7. 检查卡牌数、卡牌 ID、卡组哈希及现有 `check_deck` 规则。
8. 原子写入观察记录和精确去重卡组目录。
9. 成功持久化并校验后删除临时 replay；失败 replay 保留供诊断和重试。
10. 对精确卡组进行动态聚类并生成覆盖报告。

该管线必须与 `data/external/kaggle_replays/raw` 和现有训练数据隔离，默认不得修改或删除已有数据。

## 组件边界

### 排行榜发现器

调用 Kaggle 官方接口分页读取完整排行榜，输出稳定的 team 清单。它只负责排行榜快照，不负责 submission 或 replay。

### Submission 发现器

按 team ID 枚举公开 active submissions，保存全部可见结果，并按时间选择第一轮目标。无公开 submission 的队伍记录明确状态，不视为程序错误。

### Episode 调度器

每个目标 submission 默认选择最近 3 个 `COMPLETED` episode，并通过全局索引去重。调度器只维护任务状态，不解析 replay。

### Replay 卡组提取器

一次处理一个临时 replay，同时提取双方完整 60 卡列表及来源元数据。输出只有经过 schema 和规则校验的卡组观察；解析失败必须产生结构化错误。

### 卡组目录

保存观察级记录和按排序卡牌 ID 的 SHA-256 去重记录。相同精确卡组可以关联多个队伍、submission、episode、分数和时间，不覆盖历史来源。

### 聚类器

使用卡牌数量向量聚类，不使用排行榜分数作为距离特征。排行榜分数仅用于簇后分析和第二阶段采样权重。

## 输出契约

默认输出根目录为 `data/deck_discovery/`：

- `teams.jsonl`：排行榜快照中的队伍、排名、分数和时间。
- `submissions.jsonl`：公开 active submissions、所属队伍和选择状态。
- `episodes.jsonl`：episode 任务、来源、状态、重试次数和错误。
- `decks.jsonl`：每次有效的 60 卡观察及完整来源。
- `unique_decks.jsonl`：精确哈希、卡牌计数和聚合来源。
- `clusters.jsonl`：卡组哈希、动态簇 ID、置信度和代表卡组。
- `summary.json`：覆盖率、失败数、唯一卡组数、聚类统计和边际新增率。
- `failures/`：只有无法安全删除的失败 replay 和结构化诊断。

JSONL 写入采用临时文件加原子替换，或使用可幂等的键控状态存储后导出 JSONL。唯一键分别为 team ID、submission ID、episode ID、观察来源组合和卡组哈希。

## 覆盖与去偏策略

第一轮优先覆盖完整排行榜，而不是优先下载高分队伍的大量对局。每队取最新有效 submission，每个 submission 取最近 3 局。一个 replay 同时贡献双方卡组，因此 episode 去重后仍保留双方来源。

第一轮结束后按队伍评估卡组稳定度：

- 三次观察均为同一精确卡组：暂不补采。
- 观察到两套或三套卡组：为该 submission 补到最近 10 局。
- 未得到完整卡组：依次尝试该 submission 的其他完整 episode。
- 高分队伍：检查其他 active submissions，以发现历史换组。
- 新簇、噪声点或稀有簇：进入第二阶段优先补采名单。

训练阶段的高分加权不属于第一阶段聚类。第二阶段应在簇内按分数加权，并限制大簇的最大数据占比，避免全局高分加权再次造成分布塌缩。

## 动态聚类

聚类包含三层：

1. 精确层：排序后的 60 个卡牌 ID 计算 SHA-256，完全相同的卡组只保留一个实体。
2. 邻居层：用卡牌数量向量计算多重集余弦相似度和加权 Jaccard，建立近邻候选，避免全量二次比较扩展失控。
3. 家族层：使用 HDBSCAN 自动形成稳定密集簇；无法稳定归类的卡组保留为噪声或潜在新体系，不强制并入现有类别。

每个簇选择真实存在的 medoid 卡组作为代表。报告同时给出精确卡组数、稳定簇数、噪声比例、簇规模、代表卡组、分数分布和时间分布。若 HDBSCAN 在依赖或质量验证中不合适，可以替换内部实现，但必须保持“不固定簇数、允许噪声、输出置信度”的接口契约。

## 限流、恢复与临时文件安全

- 默认串行请求，成功请求之间至少间隔 2 秒。
- HTTP 429 使用递增退避，单次最长等待 5 分钟。
- 其他可重试网络错误最多重试 6 次。
- team、submission 和 episode 完成后立即持久化状态。
- 重启后按唯一键跳过已完成对象，不产生重复记录。
- 临时 replay 必须位于明确的专用目录；只删除本轮成功处理的具体文件。
- 卡组记录成功落盘并重新校验前，不得删除对应临时 replay。
- 不得递归删除现有 `data/`、原始 replay 目录或未解析目标。

CLI 至少支持：

- `--dry-run`
- `--max-teams`
- `--episodes-per-submission`，默认 3
- `--delay-seconds`，默认 2
- `--resume`
- `--keep-replays`

## 验收标准

- 排行榜团队枚举覆盖率不低于 99%。
- 有公开 submission 的团队中，submission 枚举成功率不低于 98%。
- 已选择 episode 的最终处理成功率不低于 97%。
- 所有进入唯一卡组目录的卡组均恰好 60 张、哈希一致且通过规则校验。
- 相同 episode 在一次或恢复后的运行中均不重复下载。
- 中断恢复不会产生重复 team、submission、episode、观察或唯一卡组记录。
- `summary.json` 报告各分数段覆盖率、精确卡组数、稳定簇数、噪声比例及继续采集的边际新增卡组率。
- 连续处理 1,000 个新 episode 后，若精确新卡组率低于 0.5%，允许提前结束第一轮，但报告必须说明提前停止原因和未扫描范围。

## 验证计划

先以 20 支队伍运行 smoke：验证 Kaggle 分页、submission 枚举、episode 去重、双方卡组提取、原子写入、失败保留和中断恢复。随后使用模拟响应覆盖 429、网络中断、损坏 JSON、非完整 episode、缺失卡组、非法卡组、重复 episode 和哈希冲突。

聚类测试使用人工构造的相同卡组、轻微变体、明显不同体系和孤立卡组，验证精确去重、近邻关系、稳定簇、噪声保留和代表卡组必须来自真实输入。完整运行前不得直接扫描全榜。

## 运行成本预估

6,519 支队伍按每队 3 局的未去重上限为 19,557 个 replay。按现有 replay 平均约 4 MB 估算，最坏传输量约 80 GB；双方重复 episode 和跨 submission 重叠会降低实际请求量。最终只保存卡组摘要时，长期磁盘占用预计为几十 MB，失败 replay 和显式 `--keep-replays` 除外。

默认两秒间隔意味着完整首轮可能持续 12 至 24 小时以上。实现必须把“20 队 smoke”和“全榜运行”做成两个明确步骤，smoke 验收通过后才能启动全榜采集。

## 非目标

- 本阶段不下载每个类别的海量完整训练轨迹。
- 不修改现有 MCTS、policy/value、Adapter 或训练数据。
- 不用排行榜分数参与卡组距离计算。
- 不预设 Top10 或固定类别数。
- 不抓取非公开接口，不绕过 Kaggle 认证、权限或限流。
